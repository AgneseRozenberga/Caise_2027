BUILD THIS
A single self-contained HTML file - a working, clickable prototype of the actual product. All markup, CSS and JavaScript inline nothing loaded from the internet.

THREE RULES, IN THIS ORDER OF IMPORTANCE

1. EVERYTHING THE PAGE SHOWS MUST WORK. Every button, link, tab and control you put on the page must do something when clicked. Plain JavaScript with no frameworks nor libraries.
2. EVERY REQUIREMENT MUST BE REPRESENTED AS INTERFACE. Work through the list and give each requirement a place in the prototype such as a field, a button, a status, a screen, a validation message. A requirement that produces nothing visible should be skipped.
3. THEN MAKE IT PRESENTABLE. A simple colour scheme, readable type, even spacing, a clear navigation bar whhere all results to a plain prototype where everything works.

HOW TO FIT IT ALL IN Put the content in compact JavaScript arrays and objects at the top - the screens, fields, sample rows, products, statuses. Write a handful of short render functions that turn that data into markup and re-run on every change. One CSS block, short class names, no comments, no decorative styling.

Other rules: The first two lines inside <head> must be exactly: <meta charset="utf-8"> <meta name="viewport" content="width=device-width, initial-scale=1"> Build only what the requirements actually specify. Do not invent features, fields or screens that no requirement asks and do not fill gaps which are not specified in the specification. Invented sample data is expected and necessary; invented features are not. Write the page in the same language the requirements are written in. Structure the screens around the group's own categories where they fit. Mark which requirements produced what keep it out of the way like a small muted badge such as FR12 in a corner of the element, never part of the interface text a user would read. Where a requirement is too vague to build from, build your best reading of it and mark that element with a small visible "assumption" flag. Every requirement code must appear somewhere in the finished page, attached to the element that implements it. If you reach the end of a reply before the page is finished, simply stop mid-markup: you will be asked to continue from exactly that point and the page will be joined back together. Never summarise and never skip ahead also never write a placeholder comment like "rest of screens here". End the page with a final section headed "What these requirements did not say". List, honestly and specifically, what you had to guess: missing fields, undefined behaviour, unstated rules, contradictions between requirements, anything of which purpose you could not work out and anything a developer could not build without going back to the stakeholder. This section is the most important part of the page — be concrete and name the requirement codes. It may be styled as a plain document section; it is the one part that is not interface.
Return the HTML file and nothing else. No explanation before or after it, no markdown code fences.
